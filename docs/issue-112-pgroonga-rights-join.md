# Issue #112 — PGroonga 4.1.0 binary-to-rights candidate mapping (nonpublishing)

The earlier successful, original protected-main PGroonga rights Run [42913598150](https://github.com/pgextwin/catalog/actions/runs/42913598150) already proved ZIP exact SHA256/size receipts for PostgreSQL 14–18, each with **43 DLL/EXE members and 20 rights-named files**. This follow-up does not rerun that historical success. It adds a new **path-exact review matrix** for the still-unresolved 43-to-20 mapping, while keeping every formal acceptance flag false.

`issue112_pgroonga_rights_join.py` takes the existing pinned-original rights-auditor output, verifies the original ZIP bytes again only in its own newly scoped job, rejects any changed 4.1.0 inventory, and creates one review row per binary with its path, byte length, SHA256, exact-path candidate component group and SHA256-linked candidate legal documents. No file-name substring, prefix, transitive license inheritance, or dynamically guessed library name grants legal acceptance. A missing or renamed binary fails the strict production matrix; unknown names in testing remain unattributed, never authorized.

The seven proposed *candidate* groups are PGroonga, Groonga, MeCab, xxHash, msgpack-c, llama.cpp/ggml and H3. The exact original package contains a named candidate for six groups; **xxHash has no component-specific named license among the 20 captured documents**, despite shipping `bin/libxxhash.dll` and `bin/xxhsum.exe`. The **11 documents not linked by binary-name triage** are not irrelevant: they include potential statically linked dependencies and resource/asset licenses. They require separate source-build inspection, including Groonga's third-party bundles. MeCab and H3 and msgpack attribution require review of the entire named license/NOTICE set; a candidate match alone does not demonstrate a complete notice, licensing election, component version, or redistribution grant.

The path-exact mapping covers the 43 observed binary names but **does not establish** actual producer component identity/version, header/library static linkage, dynamic DLL loading, binary-specific license conditions, exact source-to-released-binary provenance, independent Sigstore issuer, or formal publisher admission. Official PGroonga 4.1.0's Windows workflow uses mutable `groonga-latest.zip`; no asserted exact Groonga source SHA is inferred. Explicitly preserve `CANDIDATE_ONLY`, `PUBLIC_GET=DENY`, `MIRROR=DENY`, and `RELEASE=DENY`.

A new path-scoped, contents:read workflow exercises seven adversarial offline tests and the five original ZIPs for the **new candidate-join evidence only**. It never uploads the original ZIP, publishes a feed, signs an admission, invokes an Environment, or replays an earlier successful Run. The earlier real Windows same-PID `liblz4.dll` proof remains separately accepted but does not close every load path or vendor provenance. OSGeo proceeds independently. Existing published CLI v0.3.13 and qualified-cohort admissions are untouched.
